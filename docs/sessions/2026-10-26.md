**Fixes and features (all sized S or XS, merged into `dev`, closed by hand)**

## Decisions
- #24: a reset marks the address verified but never changes `status`, even when `auto_activate_on_verify` is set, so a reset can't skip an admin-approval step. Recorded on the issue.

## Learned
- **SQLite was hiding foreign-key bugs.** It ignores foreign keys unless `PRAGMA foreign_keys = ON` is set, which is why the suite never caught #21. That's now on in `tests/conftest.py`.
- **SQLAlchemy 2.1 treats a bare `postgresql://` URL as `psycopg` (v3), not psycopg2.** Use `postgresql+psycopg2://`, or install `psycopg`. This applies to the consuming apps too.
- Cards don't move to In review on their own unless the PR is linked in the Development sidebar before it merges. Closing the issue still moves the card to Done.

# Second session — 2026-10-26

Fixed `last_login` never being saved (#2), so invest can show a user's last login, and released it as v0.4.2.

## Finished

**Fix (XS, merged into `dev`, closed by hand)**
- #2 → #37: new `touch_last_login(user_id)` on `UserRepositoryInterface` and `SQLAlchemyUserRepository`, which sets the timestamp and commits it, like `set_password` and `set_verified`. `login()` calls it after the status and verification checks pass. `authenticate_user()` no longer touches `last_login`. No schema change, so no migration. A new test re-reads the user from a fresh session: it fails on the old code and passes with the fix. A second test checks that a refused login leaves `last_login` empty.

**Release**
- #38 → #39: v0.4.2. `master` fast-forwarded to `faf4077` and tagged `v0.4.2`, again a tag only, with no GitHub Release page. The README changelog flags that `authenticate_user()` no longer sets `last_login`, and that custom repository implementations need `touch_last_login()`.

## Not finished
- invest hasn't pinned v0.4.2 yet (that's done in the invest repos). Existing users will show no last login until they next sign in, since nothing was saved before.

## Decisions
- `last_login` means a token was issued, not that the password was correct. A correct password on a `pending`, `inactive` or unverified account doesn't update it. Recorded in #37.
- Failed-attempt tracking stays out of #2. It needs a new column and a migration, so it goes with #4.
- A release on its own gets its own issue (#38), because of issue-first.

The likely cause is board 13's "Pull request linked to issue" workflow being set to In progress, which is the default for new boards. Not yet checked in the browser.
