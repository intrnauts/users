## Decisions
- #41 (recorded on the issue): email change stays a self-service feature, done properly rather than removed. It's off by default. It has its own endpoints, uses a new token table rather than columns on `email_verification_tokens` or `users`, and has a revert window set in config.
- Every notice to the old address carries an action. The request notice has a cancel link, and the completion notice has a 7-day revert link. Revert is the main protection. Making the old address confirm too, or adding a waiting period, were considered and left out.
- Made in #45 and listed there for review: cancel forces a password reset as well as revert; a new request never removes a live revert link; confirm needs no login; a revert is refused with 409 if the old address has been taken since.
- Interim releases that ship part of a planned feature early: #42 gave the same behaviour #41 has with the flag off, so none of it was thrown away.

## Learned
- **Hiding a field in an app's UI doesn't close an API gap.** Anyone with a token can call the endpoint directly, which is why #42 shipped before #41.
- **This repo is public, so an issue must not name a consuming app next to a working attack.** #41 did at first and was edited, but the edit history keeps the old text. Check before posting, not after.
- **A board's "Pull request linked to issue" workflow defaults to In progress.** That's confirmed now on board 13. Orbit, dyner.z, chakri, intertainment and invest are probably the same and haven't been checked.
- **Route-level tests:** mount `create_user_router()` on a bare `FastAPI()`, set `app.dependency_overrides[get_user_service]` to the test service, and log in for real. See `tests/test_routes.py`.
